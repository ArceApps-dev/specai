# specai-audit-plan

Full-project audit with interactive triage that feeds directly into specai-plan.
Runs two audits in parallel, presents numbered findings, lets the user choose
which to address, then hands off to specai-plan for implementation.

## ABSOLUTE RULE (INQUEBRANTABLE)

**This skill is READ-ONLY until specai-plan begins. It audits, reports, and
organizes — it NEVER modifies code. Code changes happen exclusively through
specai-plan after user confirmation.**

## When to Use

- User wants a comprehensive codebase health check
- User wants to identify and prioritize improvements
- User says "audit the project", "find problems", "what needs fixing"
- User invokes `/specai-audit-plan`

## Prerequisites

Two existing skills provide the audit capabilities:
- `specai-anti-bloat` (Sub-Skill 2: Repo Audit) — finds over-engineering, dead code, unnecessary abstractions
- `specai-improve-codebase-architecture` — finds architectural friction, shallow modules, seam leakage

## The Flow

### Phase 1: Parallel Audit Execution

Run both audits concurrently:

```
Parallel execution:
├── specai-anti-bloat (Sub-Skill 2: Repo Audit)
│   → Scans entire repo for over-engineering
│   → Output: ranked findings with tags (delete/stdlib/native/yagni/shrink)
│
└── specai-improve-codebase-architecture
    → Scans for architectural friction
    → Output: friction points with severity and recommendations
```

### Phase 2: Unify Findings

Merge both audit outputs into a single numbered list:

```markdown
# Audit Findings

## Bloat (from anti-bloat audit)

1. [delete] Unused retry wrapper in src/utils/retry.ts — nothing replaces it. [-18 lines]
2. [stdlib] Hand-rolled date formatter in src/lib/format.ts — use Intl.DateTimeFormat. [-12 lines]
3. [yagni] AbstractRepository with one implementation in src/repos/ — inline it. [-25 lines]

## Architecture (from architecture audit)

4. [shallow-module] src/services/wrapper.ts — thin wrapper, no real logic. Merge with caller.
5. [seam-leakage] src/db/queries.ts exposes raw SQL types to UI layer. Hide behind repository.
6. [lack-of-locality] Adding a field requires changes in 5 files. Consolidate with schema-driven approach.
```

**Numbering is continuous across both categories.** Each finding gets one number.

### Phase 3: Save to Documentation

Write the unified findings to `docs/specai/audit-findings.md`:

```markdown
# Audit Findings — [DATE]

> Generated by `/specai-audit-plan`

## Summary
- N findings total
- X bloat, Y architecture
- Estimated reduction: -Z lines, -M deps

## Findings

### Bloat
1. ...
2. ...

### Architecture
3. ...
4. ...
```

### Phase 4: Present to User

Show the numbered list to the user:

```
Audit complete. Found N issues:

BLOAT:
1. [delete] Unused retry wrapper — [-18 lines]
2. [stdlib] Hand-rolled date formatter — [-12 lines]
3. [yagni] AbstractRepository with one impl — [-25 lines]

ARCHITECTURE:
4. [shallow-module] wrapper.ts — thin wrapper, merge with caller
5. [seam-leakage] queries.ts exposes SQL types to UI
6. [lack-of-locality] Adding field requires 5 file changes

Which ones do you want to address? (e.g., "1, 3, 5-8" or "all")
```

### Phase 5: Handle Questions and Clarifications

The user may ask questions about specific findings:
- "What does #3 actually do?" → Explain the finding with code references
- "Is #5 really a problem?" → Provide evidence and impact assessment
- "Can we combine #2 and #4?" → Evaluate if they're related

**This is a conversation, not a one-shot.** The user can ask, clarify, and refine their selection.

### Phase 6: Confirm Selection

Once the user selects items, present a summary:

```
You selected: 1, 3, 5

Summary:
- #1: Remove unused retry wrapper (bloat, -18 lines)
- #3: Inline AbstractRepository (bloat, -25 lines)
- #5: Hide SQL types behind repository (architecture, seam leakage)

Ready to create implementation plan? [Y/n]
```

### Phase 7: Handoff to specai-plan

After user confirms, construct the prompt for specai-plan:

```
I've completed a codebase audit and found the following issues. The user wants to address these specific items:

[Include selected findings with full context]

Reference: docs/specai/audit-findings.md (contains all findings)

Please create an implementation plan to address these issues.
```

Then invoke specai-plan with this context. The specai-plan flow will:
1. Create a feature branch
2. Run socratic definition to clarify scope
3. Create detailed implementation plan
4. Execute task by task with code review

**In the resulting _plan.md**, reference the audit findings:

```markdown
## Context

This plan addresses findings from a codebase audit.
Full audit report: `docs/specai/audit-findings.md`

Findings addressed:
- #1: [description]
- #3: [description]
- #5: [description]

Findings deferred:
- #2: [description] — user chose not to address
- #4: [description] — user chose not to address
```

## Integration with specai-plan

The handoff is seamless:
1. specai-audit-plan constructs the initial context
2. specai-plan takes over and follows its normal flow
3. The audit-findings.md file persists as reference
4. The _plan.md documents which findings are addressed vs deferred

## Examples

### Example 1: Full audit, selective implementation

```
User: /specai-audit-plan

Agent: Running audits...

Found 8 issues:

BLOAT:
1. [delete] Dead config parser — [-45 lines]
2. [stdlib] Manual JSON validation — [-20 lines]
3. [yagni] Abstract logger with one impl — [-30 lines]

ARCHITECTURE:
4. [shallow-module] utils/wrapper.ts — no real logic
5. [seam-leakage] DB types exposed to UI
6. [lack-of-locality] Feature changes require 6 file edits
7. [coupling] Service A directly imports Service B internals
8. [duplication] Same validation logic in 3 places

Which ones do you want to address?

User: 1, 3, 5, 8

Agent: You selected: 1, 3, 5, 8

Summary:
- #1: Remove dead config parser (bloat, -45 lines)
- #3: Inline abstract logger (bloat, -30 lines)
- #5: Hide DB types behind repository (architecture, seam leakage)
- #8: Extract shared validation logic (architecture, duplication)

Ready to create implementation plan? [Y/n]

User: y

Agent: [Constructs prompt and invokes specai-plan]
```

### Example 2: Audit with questions

```
User: /specai-audit-plan

Agent: [Runs audits, presents 6 findings]

User: What's #4 about?

Agent: #4 is seam leakage in src/db/queries.ts. It exports raw SQL query types
that are imported by UI components. This means UI code knows about database
structure. If you change the DB schema, UI breaks. Recommendation: create a
repository layer that hides DB types behind domain models.

User: Okay, I'll take 2, 4, 6.

Agent: [Summary and confirmation]
```

## Boundaries

**This skill does:**
- Run two audits in parallel
- Unify findings into numbered list
- Save findings to documentation
- Present findings to user
- Handle questions and clarifications
- Construct handoff prompt for specai-plan

**This skill does NOT:**
- Modify code (read-only until specai-plan)
- Create implementation plans (specai-plan does this)
- Execute code changes (specai-plan does this)
- Run per-task code review (specai-plan does this)

## Required Skills

- `specai-anti-bloat` — provides repo-wide bloat audit
- `specai-improve-codebase-architecture` — provides architectural audit

## Handoff

After triage, hand off to `/specai-plan` (a registered slash command, not a skill directory). The flow will:

1. Create a feature branch
2. Run socratic + grill-me + write-prd to clarify scope
3. Create detailed implementation plan
4. Execute task by task with code review
5. Present the HTD de aceptación, then stop at Gate UA for the user's explicit accept

## Red Flags

**Never:**
- Skip one of the audits (both must run)
- Modify code before specai-plan begins
- Present findings without numbering
- Force user to address all findings (they choose)
- Skip the confirmation step before specai-plan
- Forget to save audit-findings.md

**If audits find nothing:**
- Report "No issues found. Codebase is lean."
- Do not invoke specai-plan
